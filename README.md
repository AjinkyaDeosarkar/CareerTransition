# Legacy File Validator — Python Data Engineering Project

## 1. Project Overview

The **Legacy File Validator** is a Python-based utility that validates fixed-width transaction records generated by a legacy mainframe application before their data is migrated to a modern data platform.

In traditional mainframe environments, batch applications often process sequential files with predefined field positions and lengths. During cloud migration, validating these files before transformation and loading helps identify malformed records and preserve data quality.

This project demonstrates how Python can be used to implement legacy file validation, exception handling, data-quality checks, and reconciliation reporting.

**Project name:** `legacy-file-validator`

**Technology stack:**
- Python 3
- File handling and string slicing
- CSV processing
- Logging
- Automated testing with `unittest`
- Git and GitHub

## 2. Business Problem

A legacy payment application generates a fixed-width transaction file. Before migrating the data to a cloud platform, every record must be checked against predefined validation rules.

The validator separates records into two outputs:

- `valid_records.csv` — records that pass all validation rules.
- `rejected_records.csv` — records that fail validation, along with their rejection reasons.

The program also records processing statistics so that the source and target record counts can be reconciled.

## 3. Fixed-Width File Layout

Each input record must contain exactly 36 characters.

| Field | Starting Position | Ending Position | Width | Example |
|---|---:|---:|---:|---|
| Transaction ID | 1 | 10 | 10 | `TXN0000001` |
| Account ID | 11 | 20 | 10 | `ACC0000001` |
| Amount in Paise | 21 | 28 | 8 | `00012500` |
| Transaction Date | 29 | 36 | 8 | `20261026` |
| **Total** | | | **36** | |

Positions in the table use 1-based indexing. Python string slicing uses 0-based indexing.

```python
transaction_id = record[0:10]
account_id = record[10:20]
amount = record[20:28]
transaction_date = record[28:36]
```

The amount is stored in paise. For example, `00012500` represents ₹125.00.

## 4. Validation Rules

The program applies the following checks to each input record.

| Rule | Validation | Failure Condition |
|---|---|---|
| 1 | Record length | Record does not contain exactly 36 characters |
| 2 | Transaction ID | Transaction ID is blank |
| 3 | Account ID | Account ID is blank |
| 4 | Amount | Amount contains nonnumeric characters |
| 5 | Transaction date format | Date does not follow `YYYYMMDD` |
| 6 | Transaction date validity | Date does not represent a real calendar date |

A record is accepted only when all validation rules pass.

**Note:** The current specification does not require transaction IDs or account IDs to follow a particular alphanumeric pattern. Such checks can be added as separate business rules if required.

The rejected records should include the appropriate reasons:

- Invalid amount: record 4.
- Invalid calendar date: record 5.
- Blank account ID: record 6.
- Incorrect record length: record 7.

Record 10 should be accepted because its transaction ID is nonblank and the current rules do not prohibit letters in that field.

The reconciliation equation is:

```text
Total Records = Accepted Records + Rejected Records

```
